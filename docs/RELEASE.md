# Release

Development uses canonical Git URLs without registry version selectors. The
committed Cargo.lock fixes the z64, zcall and zconv versions and source commits. A
release version bump changes only zmcpio's package version in Cargo.toml and
Cargo.lock; it does not advance any dependency.

Registry publication uses the Project Z projection tool at commit
`8df81739982dd60c760d0d47c4f7b02df0e1db74`. The workflow checks out that revision
separately from zmcpio and verifies its Python source against its Git objects
before executing it. The tool archives the committed zmcpio source and renders
exact registry dependency versions into an isolated directory. That directory
has no Git repository and no `.cargo_vcs_info.json`.

This replaces the earlier local staging commit. The 0.5.2 archive contains Cargo
VCS metadata for that local commit, which differs from the public source tag.
The new pipeline does not rewrite that version or its tag. A subsequent release
must produce a newly verified archive.

## Source and registry validation

The supported dependency closure is exactly zmcpio → {z64, zcall}, with
zcall → zconv and no further dependencies from z64 or zconv. The source
audit checks the committed manifest and lock against actual locked Cargo
metadata. It rejects registry fallback, another Git URL or commit, extra
packages, and additional development, build, optional or target dependencies.
Dependency features must remain disabled.

`python scripts/release.py stage BUNDLE` requires a clean source checkout. It
reads the source manifest and lock from the full commit, verifies the registry
name, repository, owner, exact locked version, yank state and checksum for each
dependency, and checks the same dependency closure. It then calls the fixed
Project Z tool. The resulting source is `BUNDLE/source`; a registry Cargo.lock is
generated by Cargo and checked against both the original Git identities and
actual locked registry metadata. A missing or incompatible published dependency
stops the operation.

The original source, index and repository configuration remain unchanged. Git's
line-ending settings are overridden only while archiving, so a Windows CRLF
checkout still supplies committed LF source bytes. The projection report and
stage proof stay beside `source`, outside the package. They record the source
commit and tree, input digests, tool revision, projected manifest digests,
registry lock digest and Git-to-registry dependency mapping.

`verify-stage BUNDLE/source` reconstructs a fresh projection from the trusted
source checkout and tool revision. It compares all source paths, bytes,
executable bits and symbolic links, validates the registry lock and rechecks live
dependency metadata. Editing a sidecar cannot authorize changed source or a
different checksum. The explicit registry audit is:

```sh
cd "$REGISTRY_STAGE"
python scripts/audit.py --mode registry
```

`RELEASE_SOURCE_ROOT` must still identify the original Git-only source, and
`PROJECT_Z_TOOLS` must identify the pinned tools checkout. Running the normal
development audit on a registry projection fails.

## Archive proof

All registry package operations explicitly use `RUSTUP_TOOLCHAIN=1.100.0`.
This fixes the Cargo version used to create archive bytes; it does not change
the library's Rust 1.99.1 MSRV. Source tests still run on Rust 1.99.1 and stable.

`verify-package` checks the package identity, original projected manifest, exact
registry lock, complete Cargo publication file list and every included source
byte. Any Cargo VCS metadata is rejected. It then runs the official projection
again, installs the verified lock, invokes Cargo package in a separate target
directory and requires the rebuilt archive SHA-256 to equal the candidate
archive SHA-256. Packaging must not modify the lock. The rebuild cannot overwrite
the candidate being checked.

The resulting `zmcpio-registry-package.json` is a source and rebuild proof. It is
not an independently trusted Project Z consumer receipt. A consumer establishes
its receipt digest independently after checking the public source, publication
and reproduced archive; this workflow does not make its own candidate hash a
consumer trust anchor.

After publication, crates.io's package identity, yank state and checksum must
match the verified archive before the workflow creates a source tag or GitHub
Release. The source is tagged directly; no local registry staging commit exists.

## Running the checks locally

Install Rust 1.100.0 and check out the fixed Project Z commit in a separate
directory. Start with a clean, committed zmcpio checkout and unused staging
paths. For example, with absolute paths already chosen:

```sh
export RELEASE_SOURCE_ROOT=/path/to/zmcpio
export PROJECT_Z_TOOLS=/path/to/project-z-tools
export RUSTUP_TOOLCHAIN=1.100.0
export PYTHONDONTWRITEBYTECODE=1
export REGISTRY_BUNDLE=/tmp/zmcpio-registry
export REGISTRY_STAGE="$REGISTRY_BUNDLE/source"
export REGISTRY_TARGET=/tmp/zmcpio-registry-target
export REGISTRY_REBUILD_TARGET=/tmp/zmcpio-registry-rebuild-target
export CARGO_TARGET_DIR="$REGISTRY_TARGET"

cd "$RELEASE_SOURCE_ROOT"
python scripts/test_release.py
python scripts/release.py stage "$REGISTRY_BUNDLE"
cd "$REGISTRY_STAGE"
python scripts/audit.py --mode registry
cargo package --locked --registry crates-io
python "$RELEASE_SOURCE_ROOT/scripts/release.py" verify-package "$REGISTRY_STAGE"
cargo publish --dry-run --locked --registry crates-io
```

The Python tests use temporary real Git repositories and mock the HTTP and
Cargo boundaries. With `PROJECT_Z_TOOLS` set, staging tests exercise the actual
pinned projection implementation. Without it, they use a functional offline
projection fixture. CI provides the real tool checkout and separately executes
real registry lock generation, metadata, packaging, rebuilding and dry-run gates.

## Starting a release

The release workflow accepts patch, minor or major increments and explicit legal
SemVer. Dispatch validates only by default. Set `publish=true` on the trusted
default branch to request publication. Planning verifies ownership, checks that
the target version is unpublished, and validates the exact registry dependency
closure. Network or authentication failures stop the workflow.

Alternatively, update `.github/release-request.txt` on `main` with the intended
version. Only that path automatically triggers the release workflow. Both entry
points use the same validation and publication gates. Do not request a version
that is already published.

Linux, Windows and macOS retain the stable/MSRV matrix, no_std checks,
all-features tests, doctests, Clippy, WASM checks and independent stdio/client
smoke checks. The registry stage is audited, packaged, rebuilt and dry-run on
each release matrix entry. The ordinary CI and evidence workflows use the same
projection path for their package checks.

## Publishing and recovery

The publication job repeats source and registry checks. Before pushing, it
requires that the release commit changed only the root package version, that
all dependency identities are unchanged, and that the remote default branch
still equals the workflow's starting commit. It uses a normal fast-forward push
for the Git-only source. Cargo publish runs in the verified projection.

Only the publish step receives `CARGO_REGISTRY_TOKEN`. No login command, token
argument or credential file is needed. PRs and forks cannot enter the release
publication job. Release concurrency does not cancel an active publication.

If publication succeeds but a later tag or GitHub Release step fails, recover
that exact immutable version after verifying its source and registry checksum.
Do not republish it or repeat the version bump blindly. If publication fails,
the verified version commit may already be on main, but no release tag or GitHub
Release has been created.
